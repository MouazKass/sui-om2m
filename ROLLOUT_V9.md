### What was different about these Pis, and what was changed

1. **Network flapping: DHCP with no DHCP server.** Both Pis shipped with NetworkManager's
   "Wired connection 1" on DHCP. This subnet has no DHCP server (rpi1–3 are static), so
   every attempt timed out after 45 s (`ip-config-unavailable`), NetworkManager dropped
   the link, and retried minutes later. From outside the Pis appeared and vanished at
   random. Power was fine (`throttled=0x0`) and neither rebooted. Fix, on each Pi: the
   profile set to manual, `10.25.96.20N/24`, gateway `10.25.96.1`, DNS `192.168.36.135`
   (rpi1's values). The old profile is kept at `/root/wired1.nmconnection.pre-static`;
   `/etc/hosts` got the `127.0.1.1 rpiN-iot` line (sudo warned without it).
2. **Not routed by the VPN.** The campus VPN routes .200–.203 to the laptop but not
   .204/.205. rpi1 reaches them on the LAN, so they are reached through it:
   `deploy/inventory.tsv` has a `jump` column (`rpi1` for rpi4/rpi5), and
   `scripts/lib/inventory.sh` writes an ssh_config (`$INV_SSH_CONFIG`) with a Host block
   per node and `ProxyJump` where needed. Every script passes `-F "$INV_SSH_CONFIG"`; the
   user's `~/.ssh/config` is never touched. Adding the routes to the VPN would remove the
   hop; nothing depends on it.
3. **rpi1's sshd penalises aborted connections.** OpenSSH 10 on rpi1 has
   `PerSourcePenalties` (`noauth:1`, min 15 s). VPN-side connection aborts
   ("Software caused connection abort") count against the laptop's address, and a burst of
   them briefly locks the laptop out of rpi1 and so of everything behind it. Connection
   sharing (ControlMaster) would avoid the bursts but does not work with Git Bash's ssh.
   The protection was left on; every onboarding step is idempotent, so a step that hits it
   is simply re-run.
4. **Debian bookworm, not trixie.** rpi1–3 run trixie; rpi4/rpi5 came with bookworm
   (glibc 2.36). Docker CE is installed from docker.com with the node's own suite
   (29.9.3 vs 29.1.5/29.2.0 on rpi1–3: same major, the containers bring their own
   userland). The `sui` binary (rpi1's 1.73, and the official 1.83.1 ubuntu-aarch64
   release, checked against its GitHub digest) needs glibc 2.39, so on bookworm the
   onboarding runs it inside a throwaway `debian:trixie-slim` container on the Pi
   (`--network none`, the user's uid, only `~/.sui` mounted). The key is still generated on
   the node and never leaves it.
5. **Two onboarding defects found and fixed.** The first containerised call let Docker
   create a missing `~/.sui` as root (the step now creates it first). And the step wrote
   `external.keystore` / `external.aliases` as `[]`; the CLI needs JSON objects `{}` (as on
   rpi1–3) and refused to load the wallet. Both fixed in `scripts/onboard_node.sh` and on
   the two Pis.
6. **Legacy mount.** The CSE container still bind-mounts `/tmp/current-parent-poa` (from
   v7's `start_mn_cse.sh`; nothing in v8/v9 reads it). It is a directory on rpi1–3 and in
   every image, but `04_cutover.sh` created a missing one as an empty file, so rpi4's first
   deploy failed with "not a directory". It now creates a directory.
7. **Faucet payouts are not spendable gas (open finding, see §6).** The gas watchdog's
   faucet top-ups (`A36M5skixqKbmweGbj3dhosUc39t98Wt5GtgT27cXaDu` for rpi4,
   `oqGboSwTJfNny4YkmYsy4oQxG2KCx8JQaRWhUmXNRkc` for rpi5, 1 SUI each) landed as *address
   balance*, not as a `Coin`. The plugin's native transaction builder and the container's
   CLI pay gas only with coins, so the new nodes could not send anything. The publisher
   sent each a 0.25 SUI coin (`9SNhy1WFLjrNcnQ9RjSRyq9N4hrRJf1QhXADseJzbgLb`).
